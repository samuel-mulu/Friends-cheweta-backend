# Gameplay Architecture (after the match starts)

## 1. One authoritative loop

```
Player taps dice / token
  └─ client sends intent only: ludo:roll | ludo:move {tokenId} + commandId + expectedVersion
Server (per match, Redis lock)
  ├─ pure engine validates + applies (dice from crypto RNG, never from the client)
  ├─ Redis snapshot committed (version + 1)          ← the result
  ├─ events broadcast to match:{id} (+ admin room)
  └─ Postgres history/status/settlement (retried if it fails; never undoes the move)
Client
  ├─ applies events in version order (gap → ludo:sync)
  └─ presentation queue: dice → walk → capture → turn … (one at a time)
        └─ sounds + haptics fire from the same queue, so audio matches what is seen
```

Rules that keep it fair and smooth:

- **The client never decides outcomes.** It cannot pick a die face or a destination; it
  sends a token id and the server checks it against `legalTokenIds`.
- **Optimistic feel, authoritative result.** My die starts spinning on tap; it always
  lands on the server's value. A rejected roll just stops spinning.
- **Only the roller's die animates.** Each seat's die animates when *its owner's* roll
  is presented (per-player counter that only increases).
- **Nothing is invited early.** Tokens become tappable only after the dice presentation
  finishes, so a move can never be chosen before the roll is visible.
- **Timers are server-side.** The ring around the avatar is a display of the server
  deadline; on timeout the server plays (auto roll / first legal token, then forfeit).
- **Recovery is state, not replay.** Reconnect or resume → `match:join` + `ludo:sync`.

## 2. Board presentation (any player count)

- The board is rotated so the viewer's color is always bottom-left (classic convention);
  game coordinates never rotate.
- Each player has a corner seat: avatar (initials, color), turn countdown ring, name,
  status, and their own dice facing the board. Unused corners stay empty, so 2, 3 and
  4 players share one layout.
- Tokens walk cell by cell (150 ms hop + step sound). A captured token waits on the
  cell until the attacker lands, then flies home.
- Sounds are original assets generated by `friends-game-flutter/scripts/generate_sfx.py`;
  the mute switch is persisted per device.

## 3. Growing to 3 and 4 players

Already generic: engine (2–4 players, turn order, finishing order), runtime, timeouts,
events, the Flutter board/seats. To enable:

| Step | Change | Notes |
|---|---|---|
| 1 | `MatchCreationService`: accept `playerIds.length === mode.playerCount` | today hard-limited to 2 |
| 2 | Pairing: a **table** (N seats) instead of a 1v1 challenge | same pattern as invites: Redis record + one reservation per seated player + Lua claim; fills by lobby picks, invite code, or quick-seat; starts when full |
| 3 | Settlement policy per mode | `WINNER_TAKES_ALL` (current) or `TOP_TWO` split; stored on `GameMode` so payouts are explicit |
| 4 | 3-player colors | engine uses red/green/yellow; fine with rotation |

Leaving mid-game already works for N players (resigned players rank last; play continues).

## 4. Team play (2 vs 2), as a separate rules version

Do not change `LUDO_CLASSIC_V1`; add `LUDO_TEAMS_V1` with explicit rules:

- Partners sit opposite (red+yellow vs green+blue).
- Partners cannot capture each other and may share a cell.
- A team wins when both partners have all tokens home; finished players roll for their
  partner (common house rule, decide before building).
- Engine: `teams` in state, team-aware capture/finish checks, team winner order;
  settlement pays the team (split between partners).

## 5. Recommended next: provably fair dice

`games/ludo/dice/fairness.ts` (commit–reveal + HMAC derivation, unbiased) exists but is
not wired. For a real-money game: commit `sha256(serverSeed)` at match creation and show
it in `match:join`; mix in each player's client seed; reveal the seed at the end so any
roll can be verified. Gameplay code does not change (`DiceProvider` swap).
